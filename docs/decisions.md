# Decisions

Choices made while building, with the reason. Add to the bottom; do not rewrite history.

## Phase 0

| Decision | Reason |
| --- | --- |
| The Xcode project is generated by XcodeGen from `ios/project.yml` and is not checked in. | A hand-edited `.xcodeproj` causes merge conflicts as soon as two people add files. The spec file is short and readable. |
| The app is built in Swift 5 language mode. | Swift 6 mode turns concurrency warnings into errors. Revisit once the app has real screens. |
| Three build configurations: Debug (local server), Staging, Release. | The plan asks for a base URL per environment. The address is a build setting, read from Info.plist. |
| The server uses synchronous SQLAlchemy with psycopg 3. | Simpler to write and test than async sessions. FastAPI runs these handlers on a thread pool. The phase 7 WebSocket can still be async. |
| `GET /health` sits at the root, not under `/v1`. | The plan names it `/health`, and hosting platforms probe an unversioned path. |
| When the database is down `/health` answers 503 with the health body plus `code` and `message`. | One body serves both a monitoring probe and the app's standard error decoding. |
| Validation errors add a `fields` list to `{code, message}`. | Phase 2 must show each error beside its field. Settling the shape now avoids changing the error contract later. |
| The baseline migration is empty and does not enable PostGIS. | The plan asks for one empty migration. Phase 2's migration enables PostGIS when the first location column arrives. `/health` already reports the PostGIS version, so a staging database without it is visible now. |
| Tests need a real PostgreSQL and fail, rather than skip, without one. | A skipped test proves nothing, and SQLite cannot stand in for PostGIS. |
| Tests use `httpx2`. | The test client in the installed FastAPI and Starlette versions asks for it and warns that `httpx` is deprecated there. |
| `docker-compose.yml` pins the database image to `linux/amd64`. | Works on Intel and, through Docker Desktop's emulation, on Apple Silicon. |
| Lint settings are in a root `ruff.toml`. | One configuration for `backend/` and `scripts/`. |

## Phase 1

| Decision | Reason |
| --- | --- |
| A `schools` table plus a `school_domains` table. | One school can own several email domains (`uw.edu`, `washington.edu`). A department address such as `cs.washington.edu` finds its school by its parent domain. |
| The school list lives in `backend/app/data/schools.json` and is loaded by `python -m app.seed`, which `make migrate` and the container run. | Adding a school is a one-line data change, not a migration. An unknown `.edu` domain is still accepted and shown by its domain until named. |
| Codes are stored as a keyed hash (HMAC with the server secret), not a plain hash. | A six-digit code has a million values; a plain hash could be reversed by anyone who read the table. |
| Rate limits are counted in a database table. | No extra service to run, pay for, or lose. Revisit if sign-in traffic ever makes it slow. |
| Per-email limits are 5 codes an hour and one every 30 seconds; per-address limits are deliberately loose (100 an hour). | A whole campus can share one network address, so a tight per-address limit would lock out a dorm on launch day. |
| Tokens are stateless JWTs: access 15 minutes, refresh 60 days, rotated on refresh. The user row is loaded on every request. | Deleting or suspending an account takes effect on the next request. There is no server-side "sign out everywhere" yet; add a session table if that is needed. |
| Email goes out over plain SMTP, chosen by settings. | Every provider (Resend, Postmark, Amazon SES) speaks SMTP, so switching provider is a settings change and needs no provider library. |
| Photos are uploaded straight to storage with a short-lived link. Three backends: a local folder, any S3-compatible store, or off. | The server never handles photo bytes in production. The local folder makes `make dev` work with nothing to configure. |
| The database stores a photo's storage key (`photo_key`), not its address. The API still returns `photo_url`. | The plan's `photo_url` column would have to be rewritten if the photo host ever changed. |
| A profile photo is optional on the server. | The spec lists one photo, but making it required would block sign-up whenever storage is down. See open questions. |
| Every time in the API is UTC to the second, ending in `Z`. | The iPhone's standard date decoder rejects fractional seconds. |
| Validation messages are rewritten for students ("This can't be empty."). | The validator's own wording is shown beside form fields. |
| Real server responses are kept in `docs/contract/samples/` and decoded by the app's tests. | With two codebases and one of them uncompiled here, this is what proves the Swift models match the server. |
| The app saves the last loaded profile and shows it at launch. | Opening the app offline shows your profile instead of a spinner or a sign-in screen. |
| The starting mode is remembered on the phone, not on the server. | It is a display preference. The plan asked for this in phase 3; it was small enough to do now. |
| The gender answer offers woman, man and non-binary, or no answer. | The plan's listing preference is any, women or men. Phase 4 defines how each answer matches. |

### $0 staging (added 2026-10-12)

| Decision | Reason |
| --- | --- |
| Staging runs on Render's free web service, with the database on Neon's free plan. | Render's free database is deleted 30 days after creation; Neon's free plan does not expire and includes PostGIS. Neither needs a card. |
| A third email backend, `brevo`, sends over HTTPS with Python's standard library. | Render's free plan blocks outgoing SMTP ports 25, 465 and 587. Brevo's free plan sends 300 emails a day from a single verified sender, so no domain is needed yet. |
| Photo uploads are off on staging. | Render's free disk is wiped on restart, and Backblaze B2 needs a payment for public buckets. The app already handles uploads being unavailable. |
| The app's request timeout is a build setting: 10 s for Debug, 75 s for Staging, 15 s for Release. | A sleeping free server takes about a minute to answer its first request. |
| The iPhone CI job runs only on `main` or by hand. | macOS minutes count ten times against a private repository's free allowance. |
| Staging is described in `render.yaml` (a Render Blueprint). | One click creates the service with the right settings; secrets are entered once and never committed. |

## Open questions after phase 1

- Should a profile photo be required before a student can swipe? It is optional now.
- Year is one of freshman, sophomore, junior, senior, graduate, other. Is that the right list for co-op schools with five-year programs?
- Which email-sending service and which domain? Until then staging prints codes in its log.
- Which photo store for staging and production (any S3-compatible one works)?

## Phase 2

| Decision | Reason |
| --- | --- |
| Profile photos stay optional; "quiet hours" is dropped. | Aditi's answers, 2026-10-12. |
| A listing is created as a draft holding any subset of answers; publishing (`POST /v1/listings/{id}/status`) checks every required answer and lists each missing one. | The app's flow has eight screens; saving a draft must never fail for being unfinished. |
| Rules that are never allowed (end before start, a gender preference on a whole unit, a minimum stay longer than the dates) are refused on every save, not only at publish. | The plan says a gender preference is "refused" for a whole unit. |
| A live or paused listing must stay complete when edited. Filled is final. | Renters must never see a half-finished listing; a filled sublet is history. |
| Someone else's listing that is not live answers 404, the same as one that does not exist. | Nobody can probe which listings exist. |
| Locations are stored as plain latitude and longitude for now. The public point is 120 to 180 meters away in a random direction, fixed once, and moved only when the address moves. | Phase 4 adds the PostGIS column and index for distance queries. A fixed offset can't be averaged away by asking repeatedly. |
| The migration turns PostGIS on (`CREATE EXTENSION IF NOT EXISTS postgis`). | A database without it now fails at deploy, not in phase 4. |
| Listing photos must be the lister's own listing uploads, unique across listings, 4 to 12, in display order. Removed photos are deleted from storage. | The same ownership rule as profile photos. |
| A fourth photo backend, `database`, keeps photos in a table and serves them from this server. `/dev-storage` became `/files`. | Listings need 4 photos, and staging is $0: Render's free disk is wiped on restart. The route is no longer development-only, so its name changed (logged in `docs/renames.toml`). |
| On Render, the server's public address comes from `RENDER_EXTERNAL_URL` unless `SUBLETTE_PUBLIC_BASE_URL` is set. | One fewer value to paste. |
| A short "about the housemates" line (`housemates_note`, 140 characters) was added. | The spec asks for "a line on the housemates who are staying"; the build plan's table has only a count. |
| In the app, the first tab is the deck in Renter mode and "My listings" in Lister mode. | The plan puts the full mode switch in phase 3; listers need a home now. |
| Addresses are confirmed on a map with Apple's geocoder. | Free, built in, and it needs no key. |

### Phase 3: renter mode (added 2026-10-12)

| Decision | Reason |
| --- | --- |
| Renters state their own gender as woman, man or non-binary (optional, from phase 1). Listers choose who can take a shared home: women, men, or no preference. A non-binary renter fits a place for women and a place for men. | Aditi's decision, 2026-10-12. Phase 4 enforces it on the server. A renter who hasn't stated a gender still can't see places with a preference, and the app will tell them why. |
| Renters also choose who they'd live with: women, men, or no preference, as must-have or nice-to-have (`housemate_gender`). Listers say who the housemates staying are: women, men or mixed (`household_gender`), needed to publish whenever anyone stays. | Aditi asked for the renter-side filter. The lister's gender preference is about who may move in, not who lives there, so the listing needed its own answer. A whole place, or a room with nobody staying, fits any choice. |
| Preferences are a list of `{field, value, importance}`. A yes-or-no preference is always sent as `true`; "don't care" is importance `off`. Every value's type is fixed by its field, and checked on the server. | One way to say "off". `true` can never be confused with `1`. |
| `PUT /v1/me/renter-profile` replaces the whole profile and accepts a partial one; `complete` is true once dates, budget and pin are set. `GET` answers an empty profile (not 404) before the first save. | The flow saves once at the end, and the deck (phase 4) needs only `complete`. |
| The pin lives only in `renter_profiles` and only `GET /v1/me/renter-profile` returns it. A test calls every GET endpoint in `endpoints.json` as another user and looks for the pin. | "No endpoint returns one user's pin to another" has to stay true as endpoints are added. |
| The map pin stays in the middle and the map moves under it; a tap moves it too. "My campus" searches Apple Maps for the school's own name. | iOS 17's SwiftUI map has no draggable annotation. Nothing about any one school is built in. |
| Renter mode has Deck, Map, Matches and Profile. Lister mode has Listings, Matches and Profile. The tab bar takes the mode's accent; icons and text stay ink. | Yellow icons on white fail contrast. |
| The /health status card moved from the Deck tab to the bottom of Profile. | The Deck tab now shows the renter's search. |

### Phase 4: matching engine (added 2026-10-12)

| Decision | Reason |
| --- | --- |
| `is_eligible`, `score` and `reasons` take plain values (a `Renter` and a listing) and touch no database or clock. `failures` lists every rule broken; `is_eligible` is "no failures". | Every rule is tested directly, in both directions, and the diagnostics count the same failures the deck applies. |
| A stay is the overlap of the listing's dates with the renter's, each end allowed to move by the renter's flexibility, never more than the renter wants. No overlap at all is a failure, even when the listing has no minimum stay. | The plan's "stay shorter than min_stay_days" left a zero-day stay eligible; a place for the wrong months is not a match. |
| Rent over budget is not a filter: it costs points, reaching zero rent points at 25% over. | The plan scores "rent against budget" and does not list budget among the filters. Renters can make it a filter later if they ask. |
| Distance is measured from the pin to the listing's public point, in the radius filter, the score and the `distance_m` shown. | A renter moving their own pin must never learn the exact address. |
| The deck loads every eligible listing in the circle, scores them in Python and returns the top 20 (up to 50). The database narrows by status, owner, end date and circle (`ST_DWithin` on a partial GiST index of the public point); every fit rule runs in one place. | About 30 ms for a seeded renter, well under the 300 ms target. One copy of each rule. |
| Ties go to the newer listing (`published_at`), then the id. | The plan says newer listings break ties; the id makes the order stable. |
| Diagnostics count, for each rule, how many listings in the circle break it, and name the must-have that keeps out the most. With nothing in the circle, the radius is the answer. A renter with no stated gender is told how many places have a preference and to add a gender. | The plan's empty-deck message, plus the "the app tells them so" rule. |
| The deck answers 409 `profile_incomplete` or `renter_profile_incomplete` until both are done. | Matching needs smokes, pets, dates, budget and pin. |
| Listings already swiped (phase 5) and blocked users (phase 7) are not excluded yet; the place to add them is marked in `services/deck.py`. | Those tables don't exist yet. |

### Phase 5: swipe decks and matches (added 2026-10-13)

| Decision | Reason |
| --- | --- |
| One `swipes` table for both sides: `side` is `renter` (a renter on a listing) or `lister` (a lister on a renter who liked it). Unique on side, listing and renter; the app's own `swipe_id` is unique too. | "Sending the same swipe twice changes nothing" is then the database's job, including two copies arriving at the same moment. |
| The same swipe again answers 200 with `created: false` and the first answer, match included. The opposite swipe answers 409 `already_swiped` until undone. | A retry must look like success; changing your mind goes through undo. |
| The match is made by the lister's like, in the same transaction as the swipe, with `INSERT … ON CONFLICT DO NOTHING` on (listing, renter). A lister can only swipe on someone who liked the listing and still fits it. | One like can never make a match, and ten copies of the second like make one. Tested with ten threads. |
| A renter may pass on any live listing but like only one that fits them. | The server never relies on the app to filter. |
| Undo takes the caller's last swipe only (renter swipes as one list, a lister's per listing), named by its `swipe_id`, and never one that made a match. Undoing a swipe already undone answers 404 `nothing_to_undo`, which the app treats as done. | Undo by id is safe to retry. |
| Saving a listing takes it out of the deck until unsaved. `GET /v1/saved` lists live saved listings. | The plan lists save and unsave; without a list, saved listings would be lost. |
| The deck leaves out listings already swiped or saved. Diagnostics report them as `seen`, so an empty deck says "you've seen everything", not "nothing nearby". | |
| "Notify me" on the empty deck saves `notify_new_listings` on the renter profile. Nothing is sent until notifications arrive in phase 7. | A small flag now; the plan puts notifications in phase 7. |
| The app queues swipes in a small outbox kept on the phone: sent in order, kept while offline or when the server answers 5xx, 429 or 401, dropped with the server's message on any other refusal. Each queued swipe belongs to one account. | Offline then online must never create a duplicate, and a different account on the same phone must never send someone else's swipes. |
| Lister mode gains a Renters tab (pick a listing, swipe on its interested renters). The lister sees name, photo, year, program, bio, school, wanted dates and how the renter meets each filter; never the renter's pin or budget. | "Lister deck: pick a listing, then swipe on its interested renters." |
| Matched listings still show only the public point. | The exact address for matches arrives with the map in phase 6 and chat in phase 7. |

## Known gaps after phase 2

- Photos uploaded in the editor and then abandoned (the editor closed without saving) stay in storage. A clean-up job belongs with phase 8's expiry job.
- Listings do not expire yet (phase 8).

## Known gaps after phase 1

- The phase 1 iPhone code builds and its unit tests pass on GitHub's Mac (2026-10-12). Nobody has used it in the simulator yet.
- Presigned upload links cannot enforce a size limit on S3-compatible stores (the local store does). The app shrinks photos to 1600 pixels before uploading.
- If storage is unreachable when an account is deleted, the photo file is left behind and logged. The account is still deleted.
- No App Store privacy manifest yet (`PrivacyInfo.xcprivacy`). Needed before submission in phase 9.
- Nothing is deployed to staging yet.

## Known gaps after phase 0

- The iPhone app has not been compiled. It was written without a Swift toolchain and reviewed by reading. The first `make ios-test` on a Mac is the real check.
- Not deployed to staging. That needs a hosting account.
- GitHub Actions has not run. That needs the repository on GitHub.
- `docker-compose.yml` and `backend/Dockerfile` are syntax-checked but the images could not be pulled where this was built. The server was verified against a locally installed PostgreSQL 16.15 with PostGIS 3.4.2.
- Magenta on ink is 3.5:1, below the 4.5:1 minimum. This matters for dark mode in phase 9.
